# Погодження advanced variant

Джерело: відповідь викладача, передана користувачем у цьому чаті 09.11.2026.
Це збережена копія наданого тексту, а не незалежна перевірка листування.

## Текст, наданий для погодження

1. Відкликання ініціюватиме сам користувач кнопкою «Вийти з усіх пристроїв». Планую додати POST /api/users/{userId}/sessions/revoke-all. Сервер перевірятиме автентифікацію, відповідність userId поточному principal, CSRF-токен і повторно введений пароль. Відкликання чужих сеансів не дозволятиметься навіть адміністратору. Перевірку пароля обмежу rate limiting. Операція записуватиме audit event: subject, action, resource, result, time і traceId.
2. Використаю UpdateSecurityStampAsync та ValidationInterval = TimeSpan.Zero. Завдяки цьому старі cookie відхилятимуться на наступному захищеному запиті. Ціна — додаткові звернення до PostgreSQL для перевірки користувача, а під час оновлення principal можливі також читання ролей і claims. Кількість запитів і затримку виміряю тестом; для локального навчального стенда прийму цей компроміс. Для інвалідації старих antiforgery-токенів використаю стандартний IAntiforgeryAdditionalDataProvider із прив’язкою токена до дайджесту userId і SecurityStamp.
3. Поточний сеанс ініціатора також завершуватиметься через SignOutAsync. Клієнт очищуватиме CSRF-токен із пам’яті та показуватиме необхідність нового входу.
4. Перевірю два незалежні сеанси Alice та сеанс Bob. Спочатку всі виконують дозволений захищений GET. Відсутній або неправильний CSRF-токен і неправильний повторний пароль не повинні відкликати сеанси. Після успішного відкликання обидва сеанси Alice та повторно використана стара cookie отримують 401, Bob — 200. Новий вхід Alice працює. Старий antiforgery-токен навіть після нового входу дає 400 без зміни ресурсу, новий — дозволяє дію. Bob при спробі відкликати сеанси Alice отримує 403 без ефекту, анонім — 401.
5. Не включатиму значення cookie, SecurityStamp, пароля та antiforgery-токенів у скриншоти, журнали або звіт. У доказах залишу коди відповідей, результати перевірок стану та мінімальні audit-події.

## Відповідь викладача (дослівно)

етап 3 погодженно.

Під час реалізації врахуйте:

1. Параметр {userId} у маршруті зайвий, якщо він усе одно має збігатися з principal: краще POST /api/me/sessions/revoke-all. Тоді тест для Bob: його виклик відкликає лише його сеанси, сеанси Alice лишаються дійсними. Якщо параметр залишите, код відмови має відповідати вашій матриці доступу ЛР 4.
2. З ValidationInterval = TimeSpan.Zero validator оновлює cookie майже в кожній відповіді (Set-Cookie). Зафіксуйте це в замірах і перевірте, що прапорці cookie зберігаються.
3. IAntiforgeryAdditionalDataProvider глобальний: явно обробіть анонімний випадок (login). SecurityStamp беріть із claim principal, а не окремим запитом до БД. Покажіть «до/після»: без провайдера старий токен того самого користувача після нового входу проходить, з провайдером — 400.
4. Явно оберіть спосіб перевірки пароля (CheckPasswordAsync + rate limiting чи lockout) і поясніть вибір. Невдалі спроби також пишіть в audit (result = failure, без пароля). Додайте тест: перевищення ліміту дає 429 без відкликання.
5. Новий endpoint внесіть до таблиці CSRF-периметра, моделі загроз і regression pack.

Цю відповідь збережіть у доказах звіту.

## Прийняте уточнення реалізації

параметр іншого користувача відсутній. Строгий JSON-контракт відхиляє зайві поля.
